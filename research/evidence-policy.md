# Evidence Preservation Policy (D6)

Status: Phase C design artifact. Implements decision D6 of
`phase-b-provenance-terminology-audit.md` (§8 there is the supporting archaeology).
Scope: everything under `evidence/` (JSON observations/matrices, PNG screenshots,
per-case records) and its relationship to reports, tests, and fixtures.

---

## 1. Observed historical practice (fact, not policy)

Established by git archaeology (Phase B §8.1–8.2; commands reproducible):

1. Suites write machine evidence as a run side effect (`record()` in
   `tests/e2e/utils.ts:110-113`; comparison unit tests write JSON directly).
2. `chore:` commits swept resulting diffs ("refresh … regenerated by the E2E run":
   `e08522d`, `cd43c66`, `b02fe11`; first capture `f05d120`).
3. Refreshes happened IN PLACE under unchanged filenames.
4. One deletion exists: `2f13b03` removed four E15 screenshots whose NAMING was
   superseded (`*-inline-region.png`) — naming-supersession precedent.
5. Refresh commits may carry SEMANTIC evidence changes when implementation fixes
   landed between captures (confirmed: `cd43c66` committed 3 minutes after PAR-fix
   `bcd3ad7`; blind-comparison landmark coordinates shifted accordingly).
6. No written policy existed before this document.

## 2. Adopted policy

### P-1 Archived result set

Tracked `evidence/` is the archived result set backing the L0 reports. Its value is
historical: it is what the cited conclusions were measured against. It is NOT a
rebuildable cache.

### P-2 Reproducibility vs byte stability

Evidence is reproducible-in-principle and byte-unstable-in-practice (rendering
nondeterminism; sub-pixel drift documented in Phase B §8). A regeneration that
produces different bytes is not "the same evidence". Therefore:

- Do not regenerate evidence as part of documentation edits, refactors, or cleanup.
- Regeneration never happens silently or incidentally.

### P-3 Protocol-authorized regeneration only

Regeneration is legitimate only when ALL hold:

1. an explicit instruction states WHAT is being re-measured and WHY;
2. the producing source state is recorded (implementation commit(s), fixture state,
   command, engine/browser versions where applicable — matching the metadata
   conventions already used in E17/N2/N6 evidence);
3. outcomes are compared against pre-registered expectations where they exist
   (N6 suite discipline); divergences are reported, not smoothed;
4. the change lands with provenance in the commit message
   (what/why/source-state), continuing the repo's existing convention.

Browser/network-dependent evidence (E14–E17, N2 viewer probes, IIIF validator POST)
additionally requires the original environment classes (Playwright engines, unpkg
bundles, live validator); if unavailable, the task is BLOCKED, not approximated.

### P-4 Source-state linkage

Every evidence family must remain traceable to its producer:

| Family | Producer | Notes |
|---|---|---|
| `evidence/observations/*` | e2e specs via `record()` | exp-era + cross-generation probes |
| `evidence/blind-comparison/*` | `tests/blind-comparison.test.ts` | regenerated whenever that suite runs — see P-7 |
| `evidence/e14…e17/`, screenshots | corresponding specs + `cross-engine-aggregate.mjs` | engine/version metadata embedded per row (keep that convention) |
| `evidence/viewer-matrix.json`, `evidence/viewer/probe-*` | `tests/e2e/consumer-probe.spec.ts` (+ legacy `viewer.spec.ts` for observations/screenshots/viewer) | network-dependent |
| `evidence/n6/*` | `scripts/run-validator-suite.mts` only | edit flow per `consolidation-map.md` §2 |

Producer filenames refreshed to post-G.x names (phase H.3-1, H.1 #8 disposition);
policy substance unchanged.

Fixture families and their generator status are recorded separately in
`fixture-provenance.json`.

### P-5 Naming supersession and deletion constraints

- Evidence FILENAMES are frozen once tracked, including misspelled legacy names
  (`epx6-*.png`) that documents cite verbatim.
- Deletion is justified ONLY by naming supersession AND requires a pointer record
  preserving what was dropped and why (the `2f13b03` pattern, now explicit).
  Content-based deletion ("duplicate", "stale") is forbidden.
- Renaming for tidiness is forbidden.

### P-6 Screenshots and generated JSON

Screenshots are evidence of rendered states, equal in rank to numeric JSON; both are
covered by P-1..P-5. Byte-identical duplicates across experiment families (e.g.,
sampled e15/e17 Chromium pairs confirmed identical) are retained as independent run
records — deduplication would falsify run history.

### P-7 Working-tree hazard (operational note)

Because suites write into `evidence/` on every run, running tests during
consolidation phases can dirty the tree without any source change. Consolidation
sessions must therefore either avoid running browser suites or commit/revert
resulting evidence churn explicitly per this policy. Unit-only runs that write
comparison JSON carry the same caution.

## 3. Relationship between reports and evidence

- L0 reports cite specific evidence files; those citations are frozen with the report.
- Evidence is never edited to match a report; if they disagree, the discrepancy is
  recorded (precedent: AMB-N6-1 handling) rather than reconciled silently.
- New evidence for new questions is NEW work (research), not consolidation, and
  requires its own pre-registration discipline.

## 4. Non-goals

No backfilling of missing metadata into old evidence; no migration of evidence
layouts; no re-running of anything to "validate" consolidation. Verification of
consolidation phases uses git-level checks and existing test suites only, with the
P-7 hazard respected.
