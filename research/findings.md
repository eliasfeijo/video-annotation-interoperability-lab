# Findings — Video Annotation Interoperability Lab

Date: 2026-08-20
Status: complete (all experiments executed, evidence archived)

## Research question

Can W3C **Web Annotation** + **Media Fragments** + **IIIF Presentation (Canvas/Painting)** +
SVG represent portable, temporal, graphical overlays on video — **without inventing a new
annotation vocabulary**?

This session attempted to falsify the hypothesis:

> Web Annotation (temporal + spatial selectors) + IIIF Canvas/Painting semantics +
> Media Fragments + an SVG painting body is sufficient to describe and render
> time-segmented graphical overlays on video.

## Method (one paragraph)

A deterministic synthetic test video (`1920x1080`, 30 s, 30 fps, H.264/yuv420p, grid +
crosshair + corner markers + running PTS timestamp, generated by
`scripts/generate-video.mjs`) is played in a Vite/Chromium page. Two renderers lower the
same conceptual annotation set into a single `ResolvedOverlay[]` model and composite it
through one DOM/SVG stage:

- **Renderer A** (standards-oriented): parses a IIIF Presentation 3.0 manifest generically —
  Canvas dims/duration, AnnotationPage, Painting Annotations, `t=` temporal selector,
  `xywh=` spatial selector (pixel and `pct:`), SVG body (`readSvgRootAttrs` +
  `computeNestedSvgPlacement`). No experiment data is hardcoded.
- **Renderer B** (direct reference, deliberately non-standard): pre-positioned SVG in canvas
  space. Used only as an oracle for equality checks.

Evidence is machine-verified (Playwright + Vitest) and archived under `evidence/`:
observation JSON per experiment, PNG screenshots per time-point/aspect/state.

## Verdict

Veridiction scale used here:

- **A** — hypothesis falsified: the standard stack cannot carry the information.
- **B** — hypothesis holds for the core claim with enumerated, explicit gaps that require
  application conventions or non-standard extensions.
- **C** — hypothesis holds only for a strict subset; gaps are material for the general case.
- **D** — unverifiable without building new vocabulary.
- **E** — not enough evidence to decide.

## Verdict: **B** (supported, with explicit, documented gaps)

**The standards stack is sufficient to describe and render portable, time-segmented,
spatially-targeted graphical overlays on video**, as long as:

1. an SVG body is carried as a `painting` annotation whose `Image` resource has
   `image/svg+xml` format;
2. the active time window is expressed with Media Fragments `t=` (interpreted as a
   **half-open interval** `[start, end)` — our chosen, testably consistent convention);
3. spatial targeting uses Media Fragments `xywh=` (pixel or `pct:`) interpreted as "the
   Canvas region into which the body SVG is painted";
4. z-order is derived from AnnotationPage item order;
5. the overlay compositor positions itself over the *displayed* (letterboxed) video content,
   not the element box.

The falsification attempt **failed to falsify** the hypothesis across temporal windowing,
multi-layer compositing, pixel/percent spatial targeting, coordinate-system scaling,
aspect-ratio invariance, and viewer interoperability of the video Canvas itself.

**Identified gaps (none is solvable by the core vocabulary without conventions or
extensions):**

- **Movement over time within an annotation** requires an external timeline (exp7 keyframes
  are explicitly NON-STANDARD). SVG `<animate>`/SMIL is unreliable in browser-composited,
  dynamically injected SVG — a portability risk, not a spec deficiency.
- **Coordinate-system ambiguity**: because an SVG body can carry any `viewBox`, the
  "SVG user space == Canvas space" mapping is an *interpretation* (here: paint the body into
  the targeted region per `meet`). It is identifiable and testable, but two consumers could
  enumerate it differently. A profile rule would remove this.
- **Text is not pixel-deterministic** across environments (fonts, metrics); only
  outline-surrogate bodies are.
- **Viewer support**: the reference IIIF AV player (Ramp) plays the video Canvas but cannot
  composite an SVG painting body; it throws. Standards *permit* the structure; deployed
  viewers do not yet implement it.
- **Security** of untrusted SVG bodies requires an allowlist sanitizer in the compositor.

## Implementation notes (hard-won details, useful for the report)

- FFmpeg (this build): `drawbox` needs `t=fill`; `%{pts\:hms}` breaks the filter graph parser
  (use `%{pts} s`); raw-RGB pixel probing needs explicit `-ss`/crop care.
- Chromium: nested `<svg>` elements' `getBoundingClientRect()` reports the bounding box of
  painted content, not the attribute viewport box — compute region geometry from the declared
  viewport instead.
- Vite dev server serves unknown paths its `index.html` SPA fallback: a wrong manifest name
  surfaces as `JSON.parse` of an HTML doctype (caught our text/security manifest-name bug).
- CSS id selectors outrank class rules: the aspect-preset classes were silently inert until
  the base rule was made a class selector.
- `innerHTML`-injected `<script>` does not execute (no `defer` semantics) — good baseline
  defense; attribute handlers remain inert until dispatched.
